# 音声駆動ターミナル（仮称: VoiceTerm）— 要件定義 & 設計メモ

- 作成日: 2026-06-03
- 著者: Claude Code（北國さんとのセッションより）
- ステータス: ドラフト（着手前）
- 位置づけ: 既存の cmux 上でのフック実装が macOS の制約で行き詰まったため、**音声 I/O をネイティブに内蔵したターミナルアプリ**を新規開発する方針に転換。本書はその要件と、今日得た知見（同じ轍を踏まないため）をまとめたもの。

---

## 1. 背景 / モチベーション

北國さんのワークフローは、**cmux 上で Claude Code セッションを 5 個前後、並列で走らせる**こと。各セッションが処理を終えると、結果が音声で読み上げられる（TTS）。

理想は「**結果を耳で聞いて、そのまま声で次の指示を返す**」音声ループ。とくに重要なのが——

> 5 個並列で動いていて、そのうち A セッションが読み上げ終わった。次の指示をしたいと思ったときに、**「どれが A だったか」を目で探して、そのウィンドウへ移動するのが面倒**。探さず・移動せず、聞いた直後に声で返したい。

つまり要件の核は「**完了したセッションへ、ナビゲーション無しで、声だけで返信を届ける**」。

### ユーザーの前提
- Apple Developer 登録済み。個人開発のネイティブ Mac/iOS アプリ実績あり（Viggy、YOMEL/ヨモット 等、`~/Dev/` 配下）。**ネイティブアプリ開発に抵抗なし**。
- 既存の音声入力アプリ Aqua Voice（Ctrl+F で起動/停止、フォーカス欄へ入力）を日常的に使用。
- cmux は Ghostty 系統のターミナルをクローンした流れと認識しており、「自分でも作れそう」という感触。

## 2. ゴール（一言で）

**並列の各ターミナルセッションに対し、TTS（読み上げ）と STT（聞き取り）をネイティブに内蔵し、「聞いた直後に声で話すだけ」で、読み上げたセッションへ次の指示が確実に届くターミナルアプリ。**

## 3. 今日やったこと / 学び（重要）

> 次に実装する人（＝将来の自分）が同じ調査を繰り返さないための記録。

### 3.1 TTS（出力）— **完成・現在も稼働中**
Claude Code の Stop フックで、応答末尾の `<!-- TTS: ... -->` マーカーを読み上げる仕組み。
- 旧: VOICEVOX（ローカル、話者「春日部つむぎ」）。口調が好みに合わず。
- 新: **OpenAI `gpt-4o-mini-tts`** に移行。
  - エンドポイント `POST https://api.openai.com/v1/audio/speech`、`response_format: mp3`、`afplay` 再生。
  - 声 = **`marin`**、`speed: 1.15`、instructions =「抑揚を抑えたフラットで落ち着いたトーンで、テンポよくやや速めに、はっきり読み上げて」。
  - フォールバック: OpenAI 失敗時 → VOICEVOX → macOS `say -v Kyoko`。
  - コスト: 実測で月 4 万文字・約 100 分 ≒ **月 ¥250 前後**。
- 実装: `~/.claude/hooks/tts-stop.sh`, `tts-worker.sh`, `tts-notification.sh`, `tts-enqueue.sh`, `tts-speakers.json`。キュー方式で 1 件ずつ直列再生。
- **この部分は満足のいく品質で完成。新アプリでもこの設定・プロンプトをそのまま流用する。**

### 3.2 STT / 音声入力ループ — 試行と、ぶつかった壁
「読み上げ後に自動で聞き取り → 文字起こし → 該当セッションへ注入」を狙って実装したが、**macOS の 2 つの根本的な壁**に阻まれた。

### 3.3 壁A: マイク権限（macOS TCC）
- cmux 配下で `ffmpeg`（avfoundation）録音を試すと、**全デバイスが完全無音（-91.0 dB）**。物理デバイス 3 種すべてで同じ → デバイスの問題ではない。
- 原因確定: **`cmux.app` の Info.plist に `NSMicrophoneUsageDescription` が無い**。宣言が無いアプリ（とその子プロセス）には macOS はプロンプトすら出さず、無音を流し込んで拒否する。許可リストに cmux が出てこないのも符合。
- → **設定では直せない。アプリ署名/Info.plist の問題。** 録音はマイク許可済みアプリ（Chrome / Aqua Voice / Claude.app 等）でしか不可能。
- 参考: 許可済みだったアプリ = Aqua Voice, Claude, Google Chrome, CleanShot X, VOICEVOX, Zoom 等。

### 3.4 壁B: TUI への文字注入が外部ツールからは不安定
cmux CLI（`/Applications/cmux.app/Contents/Resources/bin/cmux`）でセッションへ文字を送ろうとした結果——
- `cmux send <text>`: **シェル（cooked mode）には全文届く**が、**raw-mode の全画面 TUI（＝Claude Code）には最初の 1 キーしか届かない**（vi で `i` だけ届き本文が落ちる、を確認）。
- `cmux set-buffer --name X <text>` + `cmux paste-buffer --name X --surface S`（ブラケットペースト）: **単体テストでは実際の Claude プロンプトに全文が入った**（成功）。`send-key enter`（キー名は小文字）で送信も可。
- ところが **実ループでは届かなかった**。単体では通るのに本番フローで不発 → 外部プロセスからの TUI 注入はタイミング/状態に依存して脆い。
- cmux CLI の有用コマンド: `send`, `send-key <enter|escape|backspace|ctrl+c>`, `set-buffer/paste-buffer`, `read-screen`, `new-pane`, `close-surface`, `select-workspace`, `list-workspaces/panes`, `claude-hook stop`。認証は keychain 経由で**環境変数なしでも疎通**。`CMUX_WORKSPACE_ID` / `CMUX_SURFACE_ID` は各 cmux 端末に自動セットされる。

### 3.5 中間アーキテクチャ（C-Chrome）とその限界
壁A を回避するため、**マイク許可済みの Chrome** にローカル録音ページを常駐させる構成を実装した:
- ローカル小サーバ `~/.claude/voice-router/server.py`（Python 標準ライブラリのみ）。
- 録音ページ `~/.claude/voice-router/voice.html`（getUserMedia + WebAudio VAD で無音自動停止）。
- フロー: Stop フック → TTS 再生後に `POST /target`（cmux の ws/surf を渡す）→ ページが `/poll` で受けて録音 → `/audio` に音声アップロード → サーバが OpenAI `gpt-4o-mini-transcribe` で文字起こし → cmux 経由で該当 surface へ注入 + Enter。
- VAD パラメータ（流用可）: `SILENCE_RMS=0.018`, `SILENCE_MS=1800`, `NO_SPEECH_MS=8000`, `MAX_MS=25000`。
- STT: `POST /v1/audio/transcriptions`, model `gpt-4o-mini-transcribe`, `language=ja`。コストは月 ¥100 前後。
- **録音・文字起こしまでは完動**（ブラウザで認識成功を確認）。だが最後の「cmux 経由で Claude TUI へ注入」が壁B で不発。
- → Chrome を録音器にする回避は機能するが、**注入の信頼性が cmux CLI に依存する限り解決しない**。
- これらの実験ファイルは無効化済み（`~/.claude/voice-reply-enabled` 削除、router 停止）。資産として残置。

## 4. なぜ「ネイティブ・ターミナルアプリ」なのか

今日の 2 つの壁は、**ターミナルアプリを自分で持てば両方とも消える**:

| 壁 | 外部ツールでの状況 | 自前ネイティブアプリなら |
|---|---|---|
| A. マイク権限 | cmux に entitlement が無く録音不可。Chrome 等を間借りするしかない | **アプリが `NSMicrophoneUsageDescription` を宣言** → ネイティブ録音。Chrome 不要 |
| B. TUI への注入 | `cmux send` は raw-mode に届かない。paste-buffer も実ループで不安定 | **アプリが各ペインの PTY を所有** → 子プロセスの stdin に直接バイトを書き込める。注入は 100% 確実。ペースト擬装も不要 |
| セッション識別 | 「どの surface か」を外から推測 | **アプリが全セッションを把握** → 完了したペインを正確に特定し、そのペインへ直接届ける。フォーカス/ナビゲーション不要 |

加えてネイティブなら、**「今どのペインが喋っている/聞いている」を UI で明示**でき、マイクの排他制御（同時に聞くのは 1 つ）もアプリ内で自然に実装できる。

## 5. 要件定義

### 5.1 機能要件（FR）
- **FR-1 ターミナル基盤**: 複数ペイン/タブ/ワークスペースを持つターミナル。各ペインは個別の PTY を持ち、任意のプログラム（主に `claude`）を実行できる。
- **FR-2 PTY への直接注入**: 任意のペインの子プロセス stdin に、アプリから確実にテキスト + Enter を送れる（外部 CLI を介さない）。
- **FR-3 ネイティブ TTS**: セッション完了時に結果サマリを読み上げる。OpenAI `gpt-4o-mini-tts`（声 marin / フラット / speed 1.15）を既定。読み上げは 1 件ずつ直列。
- **FR-4 セッション完了の検知**: Claude Code が応答を終え入力待ちになった瞬間を検知する。手段は (a) Claude Code の Stop フックからアプリのローカル IPC を叩く（推奨・確実）、または (b) 端末出力のプロンプト状態を解析。
- **FR-5 自動聞き取り**: 読み上げ完了後、対象ペインを「聞き取り対象」にして自動で録音開始。開始は分かりやすい合図（2 音チャイム + 視覚表示）。
- **FR-6 ハンズフリー停止**: 無音 ~1.8 秒で自動確定（VAD）。加えて任意の停止ホットキー（Aqua Voice の Ctrl+F のような単一キー）も任意で。
- **FR-7 該当セッションへルーティング**: 文字起こし結果を、**読み上げたペインへ直接注入 + Enter**。ユーザーがそのペインへ移動・フォーカスする必要は一切なし。
- **FR-8 STT**: OpenAI `gpt-4o-mini-transcribe`（`language=ja`）を既定。将来ローカル（whisper.cpp）も選択可に。
- **FR-9 複数セッションの調停**: 同時に複数が完了しても、**録音するマイクは常に 1 つ**。完了順の FIFO キューで 1 件ずつ聞き取り、各々を正しいペインへ返す。
- **FR-10 状態の可視化**: 各ペインの状態（待機 / 読み上げ中 / 聞き取り中 / 文字起こし中）と、グローバルな「いま聞いています」をひと目で。
- **FR-11 ON/OFF とガード**: 音声ループ全体のトグル。無音や極短発話は送信しない。ストップワード（「おわり」「ストップ」等）で送信キャンセル。
- **FR-12 認識結果の確認モード（任意）**: 自動送信のほか、「一旦プロンプトに置いて目視 → 自分で Enter」モードも選べると安全。

### 5.2 非機能要件（NFR）
- **NFR-1 低遅延**: 読み上げ終了 → 聞き取り開始まで即時。文字起こしは数秒以内。
- **NFR-2 信頼性**: 注入は取りこぼし無し（PTY 直書きなので原理的に確実）。
- **NFR-3 低摩擦**: 既定はマウス/キー不要（VAD 自動停止）。権限付与は初回マイク許可の 1 回だけ。
- **NFR-4 コスト**: TTS+STT で月 ¥300〜400 程度（OpenAI 従量）。ローカル STT 選択時は ¥0。
- **NFR-5 配布**: Apple Developer 署名 + ノータライズ済みで自分の Mac に常用。将来配布も視野。
- **NFR-6 既存資産の流用**: 今日完成した TTS の設定・プロンプト、STT の設定、VAD パラメータをそのまま移植。

### 5.3 やらないこと（初期スコープ外）
- 既存ターミナル（cmux 等）の完全置換・全機能パリティ。まずは自分のワークフローに必要な機能だけ。
- iOS 版 / iPhone をマイクにする構成（将来検討）。
- 複数人/チーム機能。
- Claude Code 以外の高度な TUI 連携（まずは claude が確実に動けばよい）。

## 6. アーキテクチャ案

### 6.1 ベース選定（3 択）
1. **SwiftTerm ベースで自作（推奨）** — Miguel de Icaza の Swift 製ターミナルエミュレータライブラリを SwiftUI/AppKit に埋め込む。PTY 管理・入力注入を完全制御でき、差別化要素（音声層）に集中できる。マルチプレクサ機能は最小限を自前で。
2. **Ghostty を fork** — GPU 描画で高品質だが Zig + Swift で規模が大きく、音声層の差し込みに対して重い。cmux 系統の本流だが、学習/改修コスト高。
3. **スクラッチ（AppKit + 自前 VT パーサ）** — 最大の自由度だが工数過大。非推奨。

→ **まずは案 1（SwiftTerm）で MVP**。ターミナル描画の完成度より「音声ループが確実に回る」ことが価値の中心のため。

### 6.2 コンポーネント
- **Terminal Core**: SwiftTerm による端末 + PTY（`Foundation`/`posix_openpt`）。ペイン = 1 PTY + 1 子プロセス。
- **Injection**: `write(pty_master, bytes)` で子プロセス stdin に直接書き込み（テキスト + `\r`）。**ここが cmux との決定的な差**。
- **Session Lifecycle**: 各ペインで `claude` を起動。Claude Code の Stop フックが**アプリのローカルソケット（Unix domain / localhost）に「このセッション完了」を通知**（ペイン ID 付き）。アプリはどの PTY かを内部マップで把握。
- **TTS Engine**: 完了通知のサマリ（`<!-- TTS -->` 相当）を OpenAI TTS で再生。直列キュー。
- **Mic + STT**: AVFoundation でネイティブ録音（entitlement 宣言済み）。VAD（RMS）で自動停止 → OpenAI STT。
- **Arbiter**: グローバルなマイク排他 + 完了 FIFO キュー。1 度に 1 ペインだけ聞き取り。
- **Router**: 文字起こし結果を、その完了ペインの PTY へ注入 + Enter。
- **UI**: ペイン一覧 + 各状態バッジ + グローバル聞き取りインジケータ + トグル/設定。

### 6.3 音声ループのフロー
```
[ペインA: claude 応答終了]
   → Stop フックがアプリへ「A 完了 + サマリ」を通知
   → アプリ: A のサマリを TTS 再生（直列キュー）
   → 再生完了 → Arbiter が A を聞き取りキューに積む
   → マイク空き & A がキュー先頭 → 2音チャイム + A を「聞き取り中」表示
   → ネイティブ録音（VAD 自動停止 / 任意で停止キー）
   → OpenAI STT
   → 空/ストップワードでなければ A の PTY へ直接注入 + Enter
   → A が次の処理を開始（また完了したらループ）
```

### 6.4 マイク調停 / 複数セッション
- 完了は FIFO キュー。マイクは 1 本なので、A の聞き取り中に B が完了したら B はキュー末尾へ。A 完了後に B を聞き取り。
- 「今 A に返している」ことは UI で明示（どのペインがアクティブか一目で分かる）。ユーザーは移動不要。

## 8. 技術メモ / 決定事項 / オープンクエスチョン

- **決定**: 録音と注入は同一ネイティブアプリ内で完結させる（外部 CLI/ブラウザに依存しない）。これが今日の教訓の本質。
- **決定**: TTS/STT は OpenAI 従量で開始（既に動作・低コスト）。ローカル化は後段オプション。
- **OQ-1**: 完了検知は Stop フック IPC か、出力パースか。→ **フック IPC を推奨**（確実・既存の仕組みを流用）。アプリは小さなローカルソケットを listen。
- **OQ-2**: 停止は VAD のみで十分か、ホットキーも要るか。→ MVP は VAD 自動 + 任意のグローバル停止キー（Karabiner ではなくアプリ内のグローバルショートカット）。
- **OQ-3**: アプリ名。VoiceTerm は仮称。
- **OQ-4**: マルチプレクサ機能をどこまで自前実装するか（分割・タブ・ワークスペース）。MVP は最小限。
- **OQ-5**: Claude Code をアプリ内から起動する際の認証・権限プロンプトの扱い。
